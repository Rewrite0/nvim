# 更新项目文档

维护项目文档时只记录仓库中已经验证的事实，不根据惯例猜测功能。默认使用中文；保留用户指定的标题、代码、命令和专有名词。

## 工作流程

1. **检查现状**
   - 先在仓库根目录检查 `AGENTS.md`、`README.md` 和大小写变体是否存在。
   - 如果 `AGENTS.md` 已存在，绝不覆盖或重写它；只在用户明确要求时做局部补充，并保留原有指令。
   - 阅读入口文件、源码目录、插件/依赖配置、测试配置、锁文件和最近 Git 提交。

2. **建立事实清单**
   - 从实际配置提取安装步骤、开发/测试命令、目录职责、插件及其链接、支持的语言、工具链和快捷键。
   - 区分“插件负责安装的工具”和“项目或系统必须提供的命令”，注明运行前提。
   - 记录互斥或优先级规则，例如不同项目类型的识别方式；不要把未实现的能力写进文档。

3. **编辑文档**
   - 文件缺失时使用 `apply_patch` 创建；存在时只做最小增量修改。
   - `AGENTS.md` 使用 `# Repository Guidelines` 标题，保持约 200-400 字（或等量简洁内容），涵盖结构、命令、风格、测试和提交规范。
   - `README.md` 至少包含项目简介、环境要求、安装、插件说明、语言支持和常用快捷键；插件名称使用官方项目超链接。
   - 命令、路径、文件名和快捷键使用反引号；表格保持短小，复杂说明放在表格后。

4. **验证与交付**
   - 运行 `git diff --check`，检查 Markdown 标题、表格、代码围栏和链接格式。
   - 按项目实际情况运行格式检查、测试或无界面启动验证；不能运行时明确说明原因。
   - 查看 `git status --short`，只报告本次文档变更；除非用户明确要求，不执行 `git commit`。

## 维护原则

- 不删除项目已有的约定、警告或用户自定义内容。
- 不捏造仓库地址、版本要求、测试覆盖率、插件能力或快捷键；不确定时搜索源码或明确标注待确认项。
- 文档应描述当前行为，而不是未来计划。每次配置变更后优先更新受影响的插件、语言和快捷键章节。
